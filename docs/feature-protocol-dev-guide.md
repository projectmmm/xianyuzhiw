# 新增游戏功能开发指导

本文基于“黑市采购清单”功能的完整开发过程整理，目标是让后续新增类似功能时，可以快速复用同一套方法，减少在“找接口、猜参数、反复试错”上的时间。

## 适用场景

适用于这类需求：

- 游戏内已有真实功能，但工程里还没有对应入口
- 数据保存在游戏服务器端，需要同步修改
- 前端页面没有现成接口，需要自己补协议、补任务、补 UI
- 只能通过微信小游戏、小程序环境运行，不能直接在浏览器正常打开游戏

## 本次黑市采购清单功能的结论

这次已经确认并验证成功的协议如下：

- `store_getpurchase`
  - 作用：读取当前黑市采购清单
- `store_getpurchasehistory`
  - 作用：读取采购历史
- `store_setpurchase`
  - 作用：写入黑市采购清单
  - 注意：消息体必须按 BON 编码发送，直接传普通 JS 对象会失败

已验证的请求体结构：

```js
{
  purchaseCnt: 2,
  purchaseItemList: [
    { itemId: 2002, discount: 10 },
    { itemId: 2003, discount: 10 },
    { itemId: 2004, discount: 10 },
    { itemId: 1012, discount: 7 },
  ],
}
```

## 标准开发流程

### 1. 明确功能边界

先确认新增功能到底是哪一种：

- 只是“读取服务器状态”
- 只是“写入服务器状态”
- 先写配置，再执行另一个动作
- 完全独立的新任务

这一步一定要先定清楚，否则很容易像本次第一版那样，把“配置采购清单”和“执行黑市采购”错误耦合在一起。

建议在动代码前先写一句话定义目标：

> 这个功能最终是要“做什么”，而不是“顺手帮用户做别的”。

本次正确目标是：

> 提供一个独立的“一键配置黑市采购清单”功能，把本地配置写入游戏服务器。

### 2. 确认协议来源

优先顺序如下：

1. 工程现有代码
2. 游戏前端资源 / 混淆包
3. 实际运行抓包 / 抓消息
4. 服务器响应反推

排查方法：

- 全局搜索功能关键词、命令名、页面名、物品名
- 搜索可能的协议前缀，比如 `store_`、`dream_`、`car_`
- 搜索相关字段名，比如 `itemId`、`discount`、`purchaseItemList`
- 如果界面里没有现成实现，就去小游戏前端资源里找命令注册或消息处理代码

这次有用的信息来源：

- 本工程 `xyzwWebSocket.js` 的命令注册模式
- 游戏运行时抓到的 websocket 消息
- 本地浏览器 / 小程序缓存中的 LevelDB / IndexedDB 数据

### 3. 抓真实请求，不要只靠猜

如果是小游戏功能，优先抓“功能实际触发时”的真实命令。

推荐方法：

- 在微信开发者工具、小程序调试环境中观察网络行为
- 从本地缓存、LevelDB、IndexedDB 中提取 websocket 二进制消息
- 对比请求前后服务器状态变化

关键原则：

- 先确认命令名
- 再确认 body 字段
- 最后确认编码格式

本次最关键的坑就是：

- `store_setpurchase` 命令名猜对了
- 字段名也猜对了
- 但 body 如果不走 BON 编码，服务端仍然报错

所以不要只因为“字段看起来对”就认为接口已经通了。

### 4. 先做最小闭环验证

不要一开始就把 UI、批量任务、定时任务都接进去。

最小闭环应该是：

1. 能连上 websocket
2. 能发送读取命令
3. 能读到服务端真实数据
4. 能发送写入命令
5. 写入后再次读取
6. 读回结果与目标值一致

这一步验证通过后，再做工程接入。

本次采用的是“安全 no-op 写回验证”：

- 先读当前采购清单
- 再把同样的数据原样写回
- 再次读取确认服务端接受

这样可以在低风险下确认接口可写。

### 5. 工程接入的推荐顺序

推荐顺序固定如下：

1. 协议注册
2. 数据模型 / 配置工具
3. 任务执行器
4. 页面入口
5. 导入导出
6. 定时任务可选项
7. 交互优化

本次对应实现：

- 协议注册：
  - `src/utils/xyzwWebSocket.js`
- 配置工具：
  - `src/utils/batch/blackMarketConfig.js`
- 任务执行器：
  - `src/utils/batch/tasksStore.js`
- 页面与弹窗：
  - `src/views/BatchDailyTasks.vue`
- 定时任务列表：
  - `src/utils/batch/constants.js`

### 6. 写接口一定做“写后读校验”

凡是会修改服务器状态的功能，都建议统一采用：

1. 读取当前状态
2. 写入目标状态
3. 延迟等待
4. 再次读取
5. 与目标状态比对

不要只看接口是否返回成功。

原因：

- 有些接口会静默失败
- 有些接口返回成功但只部分生效
- 有些接口存在服务端清洗 / 修正逻辑

本次黑市采购清单就是通过“写后再读”确认真的写进服务器。

### 7. UI 不要直接暴露协议字段

如果用户需要自己填 `itemId`、`discount` 这种协议字段，基本一定会带来后续问题。

建议优先做两层：

- 用户层：物品名称、推荐选项、说明文案
- 协议层：`itemId`、`discount`

本次优化经验：

- 新增“常用物品”下拉
- 自动带出 `itemId`
- 自动带出推荐折扣
- 仍保留手动输入兜底

这个模式之后可以复用到任何“服务器配置型”功能。

## 建议的代码落地模板

### 协议注册

在 websocket 命令注册处补命令和响应映射：

```js
.register("xxx_get")
.register("xxx_set", { ...defaultBody })
```

响应映射：

```js
xxx_getresp: "xxx_get",
xxx_setresp: "xxx_set",
```

### 配置工具文件

为每类新功能单独建一个配置文件，负责：

- 默认值
- 归一化
- 去重
- 协议格式转换
- 比对函数

不要把这部分逻辑直接堆在页面里。

### 任务函数模板

推荐固定结构：

```js
const feature_syncConfig = async () => {
  // 初始化运行状态
  // 遍历 token
  // 建立连接
  // 读取当前状态
  // 写入目标状态
  // 写后读校验
  // 记录日志
  // 收尾释放连接
};
```

### 页面交互模板

建议固定拆成两类入口：

- 配置入口
- 执行入口

不要默认把“保存配置”和“立即执行真实任务”绑死在一起，除非产品目标就是一个合并动作。

## 后续新增功能时的快速执行清单

以后再做新功能，可以按下面清单执行：

1. 写一句话确认功能边界
2. 搜索工程里是否已有同类协议或任务
3. 找实际小游戏行为对应的真实命令
4. 确认 body 字段和编码方式
5. 做最小读写闭环验证
6. 注册 websocket 命令
7. 新建配置工具文件
8. 新增独立任务函数
9. 接页面和导入导出
10. 做写后读校验
11. 跑构建
12. 用测试号实机验证

## 本次开发中踩过的坑

### 1. 功能边界耦合错误

第一版把“配置采购清单”绑定到了“黑市一键采购”前置步骤里，行为不符合真实需求。

结论：

- 配置型功能要独立成任务
- 执行型功能保持单一职责

### 2. 默认备注错误会误导用户

`1012` 实际是“黄金鱼竿”，但默认备注曾误写成“招募令”。

结论：

- 用户可见名称必须来自统一物品表
- 不要手写散落备注

### 3. 命令能发出去不代表接口可用

这次 `store_setpurchase` 就是典型例子：

- 命令名对
- 字段名对
- 但编码错，接口仍然失败

结论：

- 抓真实请求
- 做写后读验证
- 不要依赖“看起来没报错”

## 建议的后续扩展

后续如果继续做同类功能，建议优先补这两个基础能力：

### 1. 通用物品字典

把常用 `itemId -> 名称 -> 默认参数` 抽成统一表，多个功能共用，避免到处重复写。

### 2. 协议验证脚本

增加一个独立的本地验证脚本，用于快速测试：

- 登录
- 建 websocket
- 发单条命令
- 打印响应
- 可选写后读验证

这样以后新增功能时，不用每次都先把 UI 写出来再验证协议。
